## 二、已经解决或已建立防护的问题

### 1. 业务领域从职业规划迁移到医疗后，旧接口和语义容易残留

**问题表现**

- 原系统包含职业规划、求职、岗位和简历相关接口及数据结构。
- 如果前后端同时保留新旧入口，会造成错误请求、错误会话类型以及额外的 8082 服务依赖。
- 医疗场景不能沿用普通聊天产品的定位，必须增加风险提示、证据约束和人工审核边界。

**解决方式**

- 后端核心入口已迁移为 `/api/ai/medical/**`、`/api/knowledge-base/**`、`/api/tasks/**` 和 `/api/ai/workflows`。
- 删除职业规划、Career Agent 和简历服务依赖，医疗会话类型统一为 `medical` 或 `agent`。
- README 和前端迁移报告明确要求清理 `/api/resumes`、`career-agent`、`advisor` 和 8082 相关代码。
- 医疗输出被限定为健康教育、资料解释、循证检索和安全分诊支持，不替代医生、药师或急救服务。

### 2. 流式对话若使用 GET 查询参数，会泄露敏感健康信息

**问题表现**

- 原生 `EventSource` 只支持 GET，问题文本容易进入 URL、浏览器历史、代理日志和监控系统。
- SSE 中断后，前端容易把不完整内容当作完整医疗建议。

**解决方式**

- 医疗 SSE 接口改为 `POST + JSON body`，前端应使用 `fetch + ReadableStream` 解析事件。
- 普通流式对话兼容“HTTP 流结束”，多步 Agent 兼容 `[DONE]`，并使用 `AbortController` 主动停止。
- 日志仅记录调用状态和载荷长度，不打印提示词、回答正文、患者资料或 OSS 预签名 URL。

### 3. 仅依赖大模型识别急症，响应不确定且可能延误

**问题表现**

- 胸痛、呼吸困难、意识障碍、疑似卒中、严重过敏、大量出血、药物过量和自伤风险不能等待模型自由生成。
- 模型可能弱化风险、遗漏急救动作，或在证据检索前给出不恰当建议。

**解决方式**

- 增加 `MedicalSafetyService`，在同步对话、SSE、RAG、工具对话和 Agent 调用模型前执行确定性红旗检查。
- 命中急症规则时直接返回拨打 120 或就近急诊提示，不继续执行普通生成链路。
- 工作流在任何 LLM 规划前执行确定性 `SafetyTriage`；药物、剂量、诊断及特殊人群问题强制标记为需要医生或药师审核。

### 4. RAG 容易无证据作答、伪造引用或忽略文档版本

**问题表现**

- 仅使用生成模型容易把模型常识冒充知识库证据。
- 单一路径召回可能漏掉关键词命中，重复片段还会挤占上下文。
- 医疗资料若缺少发布机构、日期、版本和审核状态，无法判断是否适用或仍然有效。

**解决方式**

- 提供 `query-with-sources` 和 `retrieve` 接口，将回答与来源分离并保留引用编号。
- 使用向量与关键词混合召回、重排序/MMR，并返回检索模式、候选数、阈值拒绝等诊断信息。
- 增加引用完整性校验、引用覆盖率、无效引用、冲突和不支持结论等验证字段。
- 上传时强制校验 `issuer`、`version`、`publishedAt`、`audience`、`documentType`，且仅允许 `ACTIVE + APPROVED` 文档进入当前检索库。
- 没有足够证据时返回拒答和空来源，不用模型常识自动补齐。

### 5. Java 与 Python 重复建索引，启动慢且会产生不必要的 Embedding 调用

**问题表现**

- Java 启动时构建内存向量库会重复 Python 侧的解析和索引能力。
- 启动过程依赖远程 Embedding，增加延迟、费用和失败点。

**解决方式**

- 主应用不再在启动阶段构建 Java 内存向量库。
- 上传、MinerU 解析、分层切块、混合检索和重排序统一交给 Python 8081 MCP，Java 负责安全校验、元数据治理和 API 编排。

### 6. Java 与 Python 跨机器时，本地文件路径无法直接共享

**问题表现**

- Java 保存后的本地路径对另一台机器上的 Python 服务不可见。
- 文件在传输或下载后可能损坏，且长期有效的下载地址存在泄露风险。

**解决方式**

- 默认使用 OSS：Java 上传原文并确认对象存在，再将短期预签名 URL 交给 Python 下载。
- Java 计算 SHA-256，Python 下载后校验内容完整性。
- `KB_STORAGE_MODE=local` 仅保留为显式本地调试路径。
- Java 21 已移除 JAXB，项目已补充 `jaxb-api`、`jaxb-runtime` 和 activation 依赖以兼容 OSS SDK。

### 7. 大文档解析耗时，请求同步阻塞且状态不可追踪

**问题表现**

- 上传、OSS 传输、MinerU 解析和索引可能耗时较长，同步等待容易超时。
- 服务重启后，内存中的运行任务会永久停留在“处理中”。

**解决方式**

- 上传保存和源文件准备成功后返回 HTTP 202、`taskId` 和 `QUEUED` 状态，后台异步解析索引。
- `AsyncTaskCenter` 持久化任务状态、进度、阶段、事件、错误和结果，并支持查询与取消。
- 服务重启时将未完成任务标记为失败，避免产生永久运行的假状态。
- 文档状态覆盖 `QUEUED`、`UPLOADING/PARSING_INDEXING`、`INDEXED` 和 `FAILED`，便于前端轮询展示。

### 8. MCP Streamable HTTP 需要握手，会话过期后调用会失败

**问题表现**

- FastMCP 需要先执行 `initialize` 与 `notifications/initialized`，不能直接调用 `tools/call`。
- 服务端清理空闲会话后，继续复用旧 `Mcp-Session-Id` 会返回 session not found。
- 明文 HTTP 的 h2c 升级与 uvicorn 兼容性不稳定；并发解析还可能冲突共享会话。

**解决方式**

- `McpToolClient` 实现完整初始化握手并维护 `Mcp-Session-Id`。
- 明确识别 session not found，重新握手后只安全重试一次；其他异常会重置会话但不盲目重放。
- 客户端在服务端超时前主动刷新空闲会话，并强制使用 HTTP/1.1。
- 解析请求通过批窗口合并，Java 侧并发设为 1，以适配 Python 当前单 worker 和共享会话限制。

### 9. 删除文档涉及本地文件、元数据、OSS 和 Python 索引，容易出现部分成功

**问题表现**

- 删除链路横跨多个存储，一处失败可能留下孤儿对象或不可见索引。
- 在索引任务仍运行时删除，可能出现“刚删完又被后台写回”的竞态。

**解决方式**

- 删除前将状态设为 `DELETING` 并取消仍在运行的索引任务。
- 先让 Python 完成幂等索引删除，再提交 Java 本地文件、元数据和 OSS 的删除。
- Python 删除失败时按配置重试并退避；失败状态保留为可安全重试，不提前破坏本地恢复依据。

### 10. 会话文件存在并发覆盖、路径穿越、损坏和旧数据兼容问题

**问题表现**

- 多请求同时读写同一会话可能丢消息或写出半文件。
- 未校验的 `chatId` 可被用于目录穿越。
- 旧版本曾出现 DTO 的 role/content 构造参数写反，升级后历史记录可能无法正常读取。

**解决方式**

- `chatId` 限制为 `[A-Za-z0-9_-]{1,128}`，并再次验证规范化后的目标路径仍位于会话根目录内。
- 使用逐会话锁串行化更新，写入临时文件后原子替换，并限制最多保留 200 条消息。
- 读取时兼容旧版 role/content 颠倒数据，也兼容旧版直接序列化的 `Message`。
- `EnterpriseMemoryService` 隔离普通医疗助手与医疗 Agent 的命名空间，并提供 Redis + TTL 模式用于多实例部署。

### 11. Agent 工具调用存在 SSRF、路径访问、并发失控和提示词注入风险

**问题表现**

- 模型若可直接调用文件操作、下载或任意网络资源，可能访问本机、内网或敏感文件。
- 工具请求过大、并发过高或执行过久会拖垮服务。
- 审计若保存原始参数，又会泄露健康信息。

**解决方式**

- 医疗 Agent 只注册医疗知识库、受控网页检索/读取、PDF 生成和终止工具，不注册任意命令执行、资源下载或文件编辑工具。
- 网页读取阻止本机和内网地址；文件相关工具使用安全路径解析器限制根目录。
- `ToolGateway` 提供禁用列表、参数大小限制、并发信号量、执行超时和固定容量审计。
- 审计仅保存参数摘要哈希，不保存完整敏感参数。

### 12. 外部依赖失败容易被错误解释为医学结论

**问题表现**

- 模型、搜索服务、Redis、OSS、MinerU 或 Python MCP 不可用时，普通错误文本可能被前端当作医疗回答。
- 搜索结果和网页正文属于不可信数据，不能直接支撑高风险结论。

**解决方式**

- 外部客户端对非成功状态、协议错误、空结果和工具错误显式抛出异常或返回 `ok=false`。
- 搜索工具在缺少 `SEARCH_API_KEY` 时明确返回配置错误。
- 网页内容按不可信输入处理，高风险结论要求已审核知识库证据和专业人员复核。
- 前端迁移约定将 5xx、流中断和空证据分别展示，避免伪装成完整医疗建议。

## 三、尚未解决的问题与建议

### 1. P0：OSS 凭据已写入版本化配置

**现状**

`tian-ai-agent-admin/src/main/resources/application.yml` 的 OSS AccessKey 配置仍包含非空默认值。这与 README 中“不得把 AccessKey 写入配置或版本库”的要求直接冲突。即使仓库未公开，也应视为凭据已经暴露。

**建议处理**

1. 立即在阿里云控制台禁用/轮换当前 AccessKey，并检查近期访问日志和异常账单。
2. 将配置改为 `${OSS_ACCESS_KEY_ID:}`、`${OSS_ACCESS_KEY_SECRET:}`，启动时若选择 OSS 模式且变量为空则快速失败。
3. 本地通过 IDE Run Configuration、受保护的 `.env` 或系统环境变量注入；生产使用 KMS/Secrets Manager。
4. 在 CI 增加 secret scanning，并检查历史提交；仅删除当前文件中的字符串不能消除 Git 历史泄露。

### 2. P0：生产认证、租户隔离与权限控制缺失

**现状**

当前文档已明确说明认证系统尚未实现。会话、任务、知识库文件、工具审计和删除接口如果直接暴露，存在越权读取或操作风险。仅依赖请求中的 `ownerId` 不能证明调用者身份。

**建议处理**

- 接入 Spring Security 与可信身份提供方，服务端从认证主体获得 user/tenant，不接受客户端自行声明身份。
- 为知识库上传/删除、工具审计、人工审核等接口配置 RBAC。
- 所有查询在仓储层强制带 tenantId/userId 条件，并增加越权测试和审计日志。
- 对健康数据补充加密、保留期限、删除、导出和患者授权流程。

### 3. P1：`mvn test` 当前失败

**本次复现结果**

- 命令：`mvn test`
- 结果：`Tests run: 33, Failures: 0, Errors: 6, Skipped: 0`，构建失败。
- 根因 A：`TianAiAgentAdminApplicationTests` 启动完整 Spring Context 时未配置 `DASHSCOPE_API_KEY`，`dashscopeChatModel` Bean 创建失败；依赖同一 Context 的 `FileOperationToolTest` 随后级联报错。
- 根因 B：`FileBasedChatMemoryEnterpriseTest` 与 `SafePathResolverTest` 在 Windows 清理 JUnit 临时目录时出现 `AccessDeniedException`。测试断言本身没有 Failure，但资源/句柄或环境权限导致扩展关闭失败。

**建议处理**

- 新增 `src/test/resources/application-test.yml`，禁用真实 AI 自动配置，或为 `ChatModel`、外部 MCP、Redis 和 OSS 提供测试 Bean/Mock；测试不得依赖真实 API Key。
- 将只测试文件工具的用例改为纯单元测试，避免无必要地加载完整 Spring Context。
- 检查临时目录内残留文件及持有句柄；确保所有流、Kryo Input/Output 和线程池在测试结束前关闭，再以显式的项目内测试临时目录复测。
- 修复后重新执行 `mvn clean test`，并在 CI 中同时覆盖 Windows 与 Linux。

### 4. P1：异常响应尚未统一

**现状**

参数、日期、状态或 `chatId` 不合法时，目前可能返回 400 或 5xx；客户端无法稳定区分用户输入错误、限流、依赖不可用和程序缺陷。

**建议处理**

- 增加 `@RestControllerAdvice`，统一返回 `code`、`message`、`requestId`、`timestamp` 和可选 `details`。
- 将 `IllegalArgumentException`/校验错误映射为 400，资源不存在映射为 404，限流映射为 429 并保留 `Retry-After`，依赖故障映射为 502/503。
- 对 SSE 在建立连接前与连接后的异常分别定义协议，连接后发送结构化 error event 并结束流。
- 返回给客户端的错误隐藏堆栈、预签名 URL、本地路径和上游敏感响应。

### 5. P1：单机 JSON/文件存储限制扩展能力

**现状**

任务、知识库元数据和默认会话记忆仍以本地文件保存。这适合单机开发，但多实例会产生状态分裂、并发写冲突和任务重复执行风险。

**建议处理**

- 任务和元数据迁移到 PostgreSQL/Redis，使用乐观锁或状态机保证一致性。
- 耗时解析任务通过消息队列分发，增加幂等键、重试、死信队列和 worker 心跳。
- 会话在生产环境切换到 Redis，并使用租户前缀、TTL 和加密策略。

### 6. P2：文档 MCP 子项目未纳入根构建

**现状**

仓库存在 `tian-doc-parse-index-mcp-server`，但根 `pom.xml` 的 `<modules>` 当前只包含 `tian-ai-agent-admin`。因此在根目录执行 `mvn test` 不会编译或测试该 MCP 子项目。

**建议处理**

- 如果它属于同一发布单元，将其加入根 Reactor，并统一 Java 版本、依赖管理和 CI。
- 如果它应独立发布，在 README 和流水线中明确独立构建命令、版本兼容矩阵及契约测试。

### 7. P2：测试基础设施存在未来 JDK 兼容警告

**现状**

测试日志显示 Mockito 正在动态附加 Byte Buddy Agent；未来 JDK 将默认禁止这种动态加载方式。

**建议处理**

- 按 Mockito 当前版本文档，在 Maven Surefire 的测试 JVM 中显式配置 `-javaagent`。
- 将该配置加入 CI，避免升级 JDK 后 Mock 测试突然全部失效。

## 四、建议处理顺序

1. **立即处理安全事件**：轮换 OSS 凭据、清理配置默认值、扫描历史和访问日志。
2. **恢复测试基线**：隔离外部依赖、修复 Windows 临时目录清理，使 `mvn clean test` 全绿。
3. **补齐认证授权**：在任何公网或多人环境部署前完成认证、租户隔离和 RBAC。
4. **统一异常协议**：稳定前后端联调行为，并防止技术错误被误展示为医疗结论。
5. **完善构建与 CI**：决定文档 MCP 的模块归属，增加多平台构建和契约测试。
6. **为生产扩展存储**：将单机任务、元数据与会话状态迁移到共享基础设施。

## 五、后续维护规则

- 每次解决问题时补充：发现方式、根因、修改点、验证命令和结果。
- “已解决”必须有代码或测试证据；仅有设计文档时标记为“计划中”或“部分解决”。
- 不在问题记录、日志、Issue 或截图中粘贴 API Key、患者信息、完整预签名 URL和生产数据库连接串。
- 每次发布前至少执行：密钥扫描、`mvn clean test`、接口契约测试、知识库上传/查询/删除闭环测试和急症红旗回归测试。
